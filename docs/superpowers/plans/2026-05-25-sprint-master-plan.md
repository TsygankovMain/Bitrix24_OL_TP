## Sprint 0 — Foundation & Local Dev

**Цель:** дать разработчику среду, в которой можно запустить весь стек локально и установить приложение в тестовый портал Б24.

**Артефакт:** `docker-compose up` поднимает все сервисы (Postgres, RabbitMQ, Node-backend, Nuxt-frontend); OAuth-flow в тестовый портал успешно завершается; страница настроек приложения открывается в iframe и показывает «hello, *имя портала*».

### Stories

| ID | Story | AC |
|---|---|---|
| S0.1 | Выбор Node.js-бэкенда, удаление неиспользуемых PHP/Python из стартера | `backends/php/` и `backends/python/` удалены; `docker-compose.yml`, `makefile` обновлены; `docker-compose up` запускается без ошибок |
| S0.2 | Локальный стек поднимается одной командой | `make dev` (или эквивалент) поднимает postgres+rabbit+backend+frontend; все health-checks зелёные |
| S0.3 | OAuth install flow с тестовым порталом Б24 | На портале (бесплатный пробный) приложение устанавливается; `portals` row создаётся в БД; access_token и refresh_token зашифрованы |
| S0.4 | Размещение `SETTINGS` placement в манифесте приложения | В портале появляется пункт «Настройки приложения» в меню; кликабельно, открывает iframe |
| S0.5 | «Hello world» страница настроек на Nuxt 3 | Страница в iframe рендерит «Привет, *домен портала*»; AUTH_ID валидируется через `app.info`; JWT выдаётся бэком |
| S0.6 | Минимальная CI: lint + typecheck на PR | GitHub Actions: при открытии PR в `main` — запускается lint и typecheck Node-бэка и Nuxt-фронта; статус виден в PR |
| S0.7 | Замена стартерского `README.md` и `CLAUDE.md` под наш проект | README отражает наш проект (название, цель R&D); CLAUDE.md адаптирован под наш стек и конвенции |

### Out of scope
- Деплой на staging — оставляем на Sprint 5.
- Любая логика, связанная с email — Sprint 1+.

### Зависимости
Нет (это первый спринт).

### Риски
- **R0.1** — оказывается, что стартерский OAuth-flow не работает с нашей версией Б24-API. *Митигация:* первая задача S0.1 — поднять локально и попробовать OAuth до того, как браться за остальное.
- **R0.2** — удаление PHP/Python из стартера ломает общие docker-compose сервисы. *Митигация:* удаляем в отдельной ветке, проверяем `make dev` до мержа.

### Оценка
- Opus (planning + review): **~150K токенов**
- Haiku агенты: **3-4 агента × ~50K = ~200K токенов**
- Срок: 1 неделя

## Sprint 1 — Подключение ящика

**Цель:** дать админу портала возможность через UI ввести IMAP/SMTP-креды и сохранить их в зашифрованном виде, привязав к выбранной линии ОЛ.

**Артефакт:** на странице настроек админ заполняет форму (email + IMAP + SMTP + выбор линии); приложение проверяет соединение с реальным IMAP/SMTP-сервером; при успехе — пишет `mailboxes` row в БД с зашифрованными паролями; статус «подключено» отображается.

### Stories

| ID | Story | AC |
|---|---|---|
| S1.1 | Миграции БД: `portals`, `mailboxes` | Таблицы созданы по спеке (раздел 5.2); поля `*_password`, `*_token` имеют тип `BYTEA` |
| S1.2 | Слой шифрования (libsodium sealed box) с master-key из env | Запись/чтение зашифрованных полей работает; unit-тесты на encrypt/decrypt round-trip |
| S1.3 | Backend-эндпоинт `POST /api/mailbox/test-connection` | Принимает IMAP/SMTP-параметры, делает реальные коннекты (`imapflow`, `nodemailer.verify`); возвращает success/error с понятной причиной |
| S1.4 | Backend-эндпоинт `GET /api/lines` | Дёргает `imopenlines.config.list.get` на портале; возвращает список линий ОЛ для выпадающего списка |
| S1.5 | Backend-эндпоинт `POST /api/mailbox` | Сохраняет mailbox в БД (с шифрованием), проверяет конфликт с `mailservice.mailbox.list` (warning, не блок) |
| S1.6 | Frontend: форма «Подключить ящик» на Nuxt 3 | 8 полей формы; кнопка «Проверить соединение»; кнопка «Сохранить» |
| S1.7 | Frontend: статусный блок «Ящик подключён» | После сохранения форма заменяется на блок «✓ Подключено: *email*, линия *name*» + кнопки «Изменить» / «Отключить» |
| S1.8 | E2E flow в локалке: установка → форма → сохранение | Ручная проверка: пройти весь путь от установки приложения до «ящик в БД» без ошибок |

### Out of scope
- Реальный опрос ящика — Sprint 3.
- Уведомления админу — Sprint 5.

### Зависимости
- Sprint 0 (рабочая локалка, OAuth, страница настроек).

### Риски
- **R1.1** — IMAP/SMTP-проверка занимает >10 сек на медленных серверах, UX страдает. *Митигация:* делаем проверку асинхронной с прогресс-индикатором; таймаут 15 сек.
- **R1.2** — `imopenlines.config.list.get` возвращает странный формат при разных версиях Б24. *Митигация:* тестируем на cloud + box, заводим cassette-fixtures.

### Оценка
- Opus: **~250K токенов**
- Haiku: **5 агентов × ~80K = ~400K токенов**
- Срок: 1 неделя

## Sprint 2 — Email Parser & Data Layer

**Цель:** изолированный, юнит-тестируемый модуль парсинга писем (без интеграций с Б24). Готовая модель `email_message_map`.

**Артефакт:** библиотека `domain/email/EmailParser` принимает raw IMAP-сообщение, возвращает структуру `{ subject, plainBody, attachments[], from, messageId, inReplyTo }`. Юнит-тесты на 5 реальных писем (Outlook, Gmail, Mail.ru, Яндекс, Exchange) проходят. Миграция БД для `email_message_map` применена.

### Stories

| ID | Story | AC |
|---|---|---|
| S2.1 | Миграция БД: `email_message_map` + индексы | Таблица создана по спеке; индексы `idx_email_map_chat`, `idx_email_map_msgid` есть |
| S2.2 | Модуль `EmailParser.parse(raw)` | Принимает Buffer IMAP-fetch результата; возвращает структуру; юнит-тесты |
| S2.3 | Утилита `trimQuotedText(text)` | Обрезает `>` цитаты и `On … wrote:` блоки; юнит-тесты на 5 реальных писем |
| S2.4 | Утилита `htmlToPlain(html)` | Конвертирует HTML-тело в plain text без потери смысла; юнит-тесты |
| S2.5 | Сборка fixtures: 5 реальных писем | В `tests/fixtures/emails/` — 5 `.eml` файлов от разных провайдеров; написано, на чём проверяем что |
| S2.6 | Длинные письма → обрезка до 100 КБ | При теле > 100 КБ — обрезка с пометкой «*…обрезано: показано 100 КБ из N КБ*»; юнит-тест |

### Out of scope
- IMAP-коннект (это Sprint 3).
- Доставка в ОЛ (Sprint 3).

### Зависимости
- Sprint 1 (БД-инфра, миграции).

### Риски
- **R2.1** — реальные письма часто имеют MIME-аномалии (multipart с alternative + related + mixed). *Митигация:* `mailparser` покрывает 99% случаев; для оставшегося — добавляем fallback в plain text.

### Оценка
- Opus: **~200K токенов** (это чисто бэк-логика, меньше координации)
- Haiku: **4 агента × ~70K = ~280K токенов**
- Срок: 1 неделя

## Sprint 3 — Inbound Integration с ОЛ

**Цель:** соединить парсер из Sprint 2 с реальным IMAP и Открытыми линиями Б24. Письмо приходит — попадает в Чат.

**Артефакт:** на тестовом портале в линии ОЛ виден активный канал «Email»; письмо, отправленное с внешнего адреса на подключённый ящик, за ≤ 90 секунд появляется в Чате портала как сообщение клиента; вложения прикладываются; тема в первой строке.

### Stories

| ID | Story | AC |
|---|---|---|
| S3.1 | Регистрация Custom Connector в Б24 при установке | `imconnector.register` вызывается в OnAppInstall; коннектор виден в `imconnector.list.get` |
| S3.2 | Активация коннектора в линии при подключении ящика | `imconnector.activate({ CONNECTOR, LINE })` при сохранении mailbox; в UI линии видна «Email» вкладка |
| S3.3 | IMAP-poller worker (Node.js, setInterval 60s) | Отдельный Docker-контейнер; для каждого `enabled` mailbox раз в минуту — IMAP-fetch новых писем (по `UID > last_seen_uid`) |
| S3.4 | Доставка письма в ОЛ через `imconnector.send.messages` | Парсенное письмо отправляется как сообщение в коннекторе; ID отправителя = email; имя = `From` имя или адрес |
| S3.5 | Запись в `email_message_map` с `direction=inbound` | Каждое доставленное письмо → строка в map; `Message-Id` → `ol_message_id` связка для будущего threading |
| S3.6 | Обработка вложений: outload в диск Б24 → ссылка в чате | Файлы из письма прикладываются к сообщению через `disk.folder.uploadFile`; лимит 25 МБ / файл, до 5 файлов |
| S3.7 | Тема как первая строка сообщения | Формат: `📧 Тема: ...` + пустая строка + тело письма |
| S3.8 | Обработка ошибок IMAP: после 5 фейлов — disable + email админу | Счётчик ошибок в `mailboxes.last_error`; при 5 подряд — `enabled=false`; имбот шлёт сообщение админу портала |

### Out of scope
- Ответы оператора — Sprint 4.
- Уведомления в UI настроек — Sprint 5.

### Зависимости
- Sprint 2 (парсер).
- Sprint 1 (mailbox в БД, привязка к линии).

### Риски
- **R3.1** — задержка `imconnector.send.messages` + IMAP-poll = выходим за 90 сек SLO. *Митигация:* запас оставлен (60 сек polling + ~5 сек processing = 65 сек). Если упрёмся — мониторим и оптимизируем.
- **R3.2** — лимит API Б24 на батч-операции при пиковой нагрузке. *Митигация:* `disk.folder.uploadFile` идёт батчем через Entity API, остальное — последовательно (нагрузка R&D не приведёт к лимитам).
- **R3.3** — Custom Connector mounted в линию, но сообщения не приходят (часто проблема с правами scope). *Митигация:* первая ручная проверка после S3.4 — на тестовом портале.

### Оценка
- Opus: **~300K токенов**
- Haiku: **6 агентов × ~80K = ~480K токенов**
- Срок: 1 неделя

## Sprint 4 — Outbound поток

**Цель:** обратный путь. Оператор пишет в Чате — клиент получает письмо. Тред склеивается. Очередь надёжная.

**Артефакт:** оператор пишет ответ в Чате портала в email-канале; за ≤ 30 секунд клиент получает письмо с правильным `In-Reply-To`; в почтовом клиенте клиента вся переписка склеена в одну ветку; при `kill -9` сервера в момент отправки — после рестарта письмо всё равно уходит.

### Stories

| ID | Story | AC |
|---|---|---|
| S4.1 | Webhook endpoint `/api/webhooks/b24` для `OnImConnectorMessageAdd` | Принимает POST; валидирует `application_token`; парсит payload (CHAT, MESSAGES, CONNECTOR_USER) |
| S4.2 | Lookup originating email по `ol_chat_id` в `email_message_map` | Находит последний inbound в этом чате; берёт его `email_message_id` и `from` адрес |
| S4.3 | Производитель в RabbitMQ: задача в очередь `outbound_emails` | После валидации webhook — публикация задачи `{ mailbox_id, to, subject, text, inReplyTo, references, attachments }` |
| S4.4 | Consumer worker (smtp-sender, отдельный контейнер) | Подписан на `outbound_emails`; для каждой задачи — `nodemailer.sendMail` с правильными заголовками |
| S4.5 | Retry policy: 3 попытки с backoff 10s/30s/120s | RabbitMQ + dead-letter exchange для финальных фейлов; финальный фейл → служебное сообщение в чат |
| S4.6 | Threading: `In-Reply-To` и `References` заголовки | Из map берётся оригинальный `Message-Id`; формируются корректные заголовки; ручной тест в Gmail — все письма в одной ветке |
| S4.7 | Тема ответа: `Re: {original}` или дефолтная | Если в map есть inbound — берём его subject + `Re: `; иначе `Сообщение от {имя портала}` |
| S4.8 | Вложения из чата → SMTP attachment | Файлы из сообщения в Чате (по `disk.attached.get`) скачиваются и прикладываются к письму; лимит 25 МБ суммарно |
| S4.9 | Проверка надёжности очереди | Ручной тест: остановить smtp-sender в момент отправки → запустить → письмо в итоге доставлено |

### Out of scope
- Подсказки оператору при отправке (Phase 2).
- HTML-форматирование ответа (только plain).

### Зависимости
- Sprint 3 (есть `email_message_map` с inbound записями).

### Риски
- **R4.1** — SMTP-провайдер клиента блокирует отправку с непривычных IP (наш сервер). *Митигация:* в pilot-onboarding явно прописать «убедитесь, что ваш SMTP принимает auth с IP {наш диапазон}».
- **R4.2** — формат `disk.attached.get` различается между cloud и box версиями Б24. *Митигация:* abstraction layer в `vendor/b24.ts`, тесты на обеих версиях.
- **R4.3** — RabbitMQ-задача потерялась при отключении из-за неправильной `ack` стратегии. *Митигация:* manual ack + prefetch=1, тестируем kill-9 сценарий явно в S4.9.

### Оценка
- Opus: **~350K токенов**
- Haiku: **7 агентов × ~80K = ~560K токенов**
- Срок: 1.5 недели

### Цена точки

Эти цифры зависят от трёх главных факторов:
1. **Точность ТЗ задач для Haiku.** Чёткое ТЗ = 1 итерация, расплывчатое = 2–4 итерации. Самый большой рычаг экономии.
2. **Решения архитектурных конфликтов.** Если Haiku сделает что-то не по спеке — я возвращаю на доработку. Каждый возврат — это +1 цикл Opus-review + Haiku-rework.
3. **Объём существующего кода в контексте.** Стартер уже большой; каждая задача должна получать **минимально необходимый контекст**, а не всё подряд.

### Что я делаю, чтобы минимизировать токены

- Перед каждым спринтом запускаю `writing-plans` skill: на выходе — план с явными задачами, файлами, AC. Это инструкция для Haiku.
- Для независимых задач спринта запускаю Haiku-агентов **параллельно** (`dispatching-parallel-agents` skill).
- Code-review через `code-review` skill — структурированно, не «прочитай весь PR ещё раз».

## Порядок исполнения

1. **Сейчас:** этот мастер-план согласован → переходим в `writing-plans` skill для **Sprint 0**.
2. **После Sprint 0:** ретроспектива (что узнали, что скорректировать), затем `writing-plans` для Sprint 1.
3. **И так до Sprint 5.**

Финальный артефакт R&D — приложение на staging + готовый пилотный клиент + отчёт «гипотеза подтверждена / опровергнута» с цифрами по метрикам успеха (раздел 7 спеки).
