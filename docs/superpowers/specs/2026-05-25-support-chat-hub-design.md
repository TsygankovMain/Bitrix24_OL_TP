## 1. Гипотеза и цель R&D

**Гипотеза:**

> Команда B2B-саппорта получает заметный прирост в скорости и удобстве работы с обращениями клиентов, когда email-переписка превращается в обычный чат внутри штатного Чата Битрикс24, рядом с диалогами из мессенджеров и виджета сайта. Никаких отдельных интерфейсов, переключений между почтовиком и порталом, потери истории.

**Цель R&D** — собрать минимально жизнеспособное приложение и провалидировать гипотезу на 3–5 пилотных B2B-саппорт-командах в течение 4 недель работы пилота.

**Тип приложения:** тиражируемое приложение для Битрикс24.Маркет (облако + коробка), многотенантное, OAuth-серверное.

**Главный архитектурный принцип:** «одно окно» обеспечивает сам Битрикс — мы регистрируем email как ещё один канал Открытой линии. Своего UI inbox’а **не строим**.

## 2. Скоуп

### 2.1. Что входит в R&D

1. **Email-канал как Custom Connector к Открытым линиям.** Один IMAP/SMTP-ящик на портал; входящие письма попадают в линию ОЛ как сообщения коннектора; ответы оператора уходят SMTP.
2. **Минимальный UI настроек** — одна страница для подключения ящика, привязки к линии ОЛ, мониторинга статуса.
3. **OAuth-установка** через Маркет Битрикс24, multi-tenant.

### 2.2. Что НЕ входит (явный negative scope)

| Откладывается | Причина |
|---|---|
| Свой Inbox UI | «Одно окно» обеспечивает штатный Чат портала. Не конкурируем со встроенным UI. |
| Несколько ящиков на портал | Усложняет UI/модель/роутинг, не блокирует проверку гипотезы. Phase 2. |
| OAuth-почта (Gmail, Microsoft 365) | Каждый провайдер = отдельная верификация и review. IMAP+SMTP покрывает целевую B2B-аудиторию. Phase 2. |
| AI-бот, FAQ-ответы, suggested replies | Бот — отдельная гипотеза. Сначала валидируем базовую. Phase 2. |
| HTML-форматирование, inline-картинки | Plain text. HTML конвертируем в plain. |
| CC/BCC, Reply-To, кастомные заголовки | Связь сообщений только через `In-Reply-To` / `References`. |
| Привязка письма к произвольной CRM-карточке | Только штатный механизм OL→CRM. |
| Дублирование письма в `CRM_EMAIL` Activity | В CRM-карточке диалог отображается как чат-сессия ОЛ, не во вкладке «Почта». Явное ограничение R&D, проговаривается в pilot-onboarding. |
| Голосовые сообщения, Whisper | Phase 2. |
| Веб-поиск, RAG, KB | Phase 2 (вместе с AI-ботом). |
| Аналитика, отчёты, дашборды | Используем встроенные отчёты OL Битрикс24. |
| Темы, hotkeys, кастомизация | Только страница настроек, минимальный стиль. |

### 2.3. Принципиальные ограничения

- **Сессия ОЛ ≠ thread письма.** Если письмо в той же теме приходит после закрытия OL-сессии (таймаут/закрытие оператором) — это новая OL-сессия. В клиентском почтовике — та же ветка.
- **Письмо в CRM-карточке отображается как OL-диалог**, не во вкладке «Почта». Проговаривается в `pilot-onboarding.md`.
- **Длинные письма (>100 КБ текста)** обрезаются до 100 КБ в OL-сообщении; полный текст не сохраняется отдельно.
- **Конфликт с штатным email-tracker Битрикса** — не блокируем, показываем предупреждение в UI настроек.

## 3. Функциональные требования

### Группа A. Установка и подключение

- **FR-A.1 — Установка из Маркета.** Администратор устанавливает приложение в 1 клик из Маркета. Сразу после установки автоматически регистрируется коннектор «Email» в каталоге коннекторов Открытых линий портала.
  *Приёмка:* коннектор регистрируется через `imconnector.register` и виден в `imconnector.list.get`; в UI «Открытые линии → Каналы» появляется пункт «Email».
- **FR-A.2 — Подключение ящика.** В настройках приложения админ вводит: email-адрес, IMAP-сервер/порт/логин/пароль, SMTP-сервер/порт/логин/пароль, выбирает существующую линию ОЛ.
  *Приёмка:* перед сохранением приложение проверяет соединение с IMAP и SMTP; при ошибке возвращает понятную причину.
- **FR-A.3 — Активация канала.** После успешного подключения коннектор активируется в выбранной линии.
  *Приёмка:* в линии ОЛ во вкладке «Каналы» появляется активный канал «Email» с указанным адресом.
- **FR-A.4 — Защита от конфликта.** Если подключаемый ящик уже используется штатным email-tracker’ом Битрикса, приложение **показывает предупреждение** и предлагает выбор: продолжить или отменить. Не блокируем.

### Группа B. Входящие письма

- **FR-B.1 — Доставка письма в Чат.** Письмо, пришедшее на подключённый ящик, появляется в Чате портала как сообщение в линии ОЛ от клиента.
  *Приёмка:* письмо с тестового адреса появляется в Чате портала **за ≤ 90 секунд**.
- **FR-B.2 — Идентификация клиента.** Адрес отправителя становится идентификатором клиента в коннекторе; имя — из заголовка `From` или сам адрес.
  *Приёмка:* два письма с одного адреса попадают в один и тот же диалог.
- **FR-B.3 — Связка с CRM.** Срабатывает штатный механизм ОЛ: если email уже привязан к контакту/лиду — диалог автоматически привязывается; если нет — создаётся новый лид. Своей логики нет.
- **FR-B.4 — Тело письма.** В чат уходит plain text тела письма с обрезанной цитированной перепиской. HTML конвертируется в plain.
  *Приёмка:* Outlook/Gmail-письмо с цитатой в ответе показывается без «истории» внизу.
- **FR-B.5 — Вложения.** Файлы из письма прикладываются к сообщению в чате через диск Битрикса. Лимит — 25 МБ на файл, до 5 файлов. Превышение → пометка в тексте «Файл `{name}` пропущен: слишком большой».
- **FR-B.6 — Тема письма.** Тема прикладывается первой строкой сообщения в чате (формат: `📧 Тема: ...`).

### Группа C. Исходящие ответы

- **FR-C.1 — Отправка ответа.** Сообщение оператора в Чате портала в email-канале уходит клиенту обычным письмом.
  *Приёмка:* ответ доставляется клиенту **за ≤ 30 секунд** после отправки.
- **FR-C.2 — Сохранение треда.** Письмо-ответ имеет корректные `In-Reply-To` и `References`.
  *Приёмка:* в Gmail/Outlook вся переписка склеена в одну ветку.
- **FR-C.3 — Тема ответа.** `Re: {исходная тема}`, если был хотя бы один входящий; иначе `Сообщение от {имя портала}`.
- **FR-C.4 — Вложения в ответе.** Файлы из чата прикладываются к письму. Суммарный лимит — 25 МБ.
- **FR-C.5 — Обработка ошибок отправки.** При ошибке SMTP — 3 попытки с нарастающей паузой (10s / 30s / 120s); потом служебное сообщение в чат: «⚠ Письмо не отправлено: {причина}».
- **FR-C.6 — Надёжность очереди.** Очередь исходящих переживает рестарт сервера. Реализуется через RabbitMQ из `b24-ai-starter`.
  *Приёмка:* остановить сервис в момент отправки → запустить → письмо в итоге уходит.

### Группа D. Настройки и эксплуатация

- **FR-D.1 — Страница настроек.** Один экран с тремя зонами: «Ящик», «Линия ОЛ», «О приложении».
- **FR-D.2 — Статус ящика.** Видно время последнего успешного опроса и количество обработанных писем за 24 часа.
- **FR-D.3 — Уведомление об отключении.** Если IMAP-опрос падает 5 раз подряд — ящик помечается как «отключён», админу уходит уведомление в Битрикс24-чат через системного имбота.
- **FR-D.4 — Удаление приложения.** Деинсталляция: коннектор деактивируется, опрос ящика прекращается, данные портала удаляются через 30 дней (мягкое удаление с возможностью восстановления).

### Группа E. Нефункциональные требования

- **NFR-1 — Многотенантность.** Один экземпляр обслуживает N порталов, без перекрёстных утечек данных.
- **NFR-2 — Безопасность.** IMAP/SMTP-пароли и OAuth-токены хранятся зашифрованными; на фронтенд пароли не возвращаются.
- **NFR-3 — Наблюдаемость.** Структурные логи всех IMAP/SMTP/webhook-операций. Доступны админу R&D.
- **NFR-4 — Локализация.** Только русский. EN — Phase 2.
- **NFR-5 — Размещение.** Маркет Битрикс24, бесплатно на R&D.

### 5.1. Ключевые сценарии (data flow)

**Входящее письмо:**
1. `imap-poller` раз в минуту: IMAP-коннект → SEARCH UID > last_seen → FETCH → parse.
2. Парсер: тема, тело (plain), вложения, обрезка цитат.
3. `imconnector.send.messages` → сообщение появляется в линии ОЛ.
4. Запись в `email_message_map` (для связи `Message-Id` ↔ `ol_message_id`).
5. OL автоматически: роутинг оператору + создание/привязка лида в CRM.

**Исходящий ответ:**
1. Webhook `OnImConnectorMessageAdd` от Битрикса.
2. Достаём из `email_message_map` оригинальный `Message-Id` для `In-Reply-To`.
3. Публикуем задачу в RabbitMQ (`outbound_emails`).
4. `smtp-sender` (consumer): `nodemailer.sendMail` с правильными заголовками треда.
5. При успехе — запись в `email_message_map` (direction=outbound).

### 5.2. Модель данных (минимальная)

```sql
CREATE TABLE portals (
  id              UUID PRIMARY KEY,
  b24_member_id   TEXT UNIQUE NOT NULL,
  domain          TEXT NOT NULL,
  access_token    BYTEA NOT NULL,    -- зашифровано
  refresh_token   BYTEA NOT NULL,    -- зашифровано
  token_expires_at TIMESTAMPTZ NOT NULL,
  installed_at    TIMESTAMPTZ DEFAULT now(),
  uninstalled_at  TIMESTAMPTZ
);

CREATE TABLE mailboxes (
  id              UUID PRIMARY KEY,
  portal_id       UUID NOT NULL REFERENCES portals(id) ON DELETE CASCADE,
  email           TEXT NOT NULL,
  imap_host       TEXT NOT NULL,
  imap_port       INT NOT NULL,
  imap_user       TEXT NOT NULL,
  imap_password   BYTEA NOT NULL,    -- зашифровано
  smtp_host       TEXT NOT NULL,
  smtp_port       INT NOT NULL,
  smtp_user       TEXT NOT NULL,
  smtp_password   BYTEA NOT NULL,    -- зашифровано
  use_ssl         BOOLEAN DEFAULT true,
  ol_connector_id TEXT NOT NULL,
  ol_line_id      INT NOT NULL,
  last_seen_uid   INT,
  enabled         BOOLEAN DEFAULT true,
  last_error      TEXT,
  last_polled_at  TIMESTAMPTZ,
  UNIQUE(portal_id)
);

CREATE TABLE email_message_map (
  id               UUID PRIMARY KEY,
  mailbox_id       UUID NOT NULL REFERENCES mailboxes(id) ON DELETE CASCADE,
  email_message_id TEXT NOT NULL,
  email_in_reply_to TEXT,
  ol_chat_id       BIGINT NOT NULL,
  ol_message_id    BIGINT,
  direction        TEXT NOT NULL CHECK (direction IN ('inbound','outbound')),
  status           TEXT NOT NULL DEFAULT 'pending',
  error            TEXT,
  created_at       TIMESTAMPTZ DEFAULT now(),
  sent_at          TIMESTAMPTZ
);
CREATE INDEX idx_email_map_chat ON email_message_map(ol_chat_id);
CREATE INDEX idx_email_map_msgid ON email_message_map(email_message_id);
```

## 6. Безопасность

1. Все секреты (IMAP/SMTP-пароли, OAuth-токены) шифруются `libsodium sealed box`. Master key — env-переменная сервера.
2. OAuth-токены Битрикса живут 1 час; refresh за 5 минут до истечения, отдельный worker.
3. Webhook от Битрикса валидируется через `application_token` из заголовка.
4. Фронт → бэк: JWT короткого срока действия (15 минут), выдаётся после валидации `AUTH_ID` через `app.info`.
5. Пароли никогда не возвращаются на фронт — только пометка «••••• сохранён».
6. Логирование без секретов, даже в DEBUG.

## 7. Метрики успеха R&D

Гипотеза подтверждена, если на пилоте 3–5 B2B-саппорт-команд за 4 недели:

- **≥ 70% операторов** отвечают на email клиентам исключительно в Чате портала, не открывая внешний почтовик. *Измеряем:* опрос команд в конце пилота + анализ логов «отправлено через нас vs. отправлено напрямую».
- **Среднее время ответа на тикет снижается ≥ 20%** против бейзлайна. *Измеряем:* сравнение времени первого ответа в email vs. в нашем потоке. Бейзлайн снимаем перед пилотом.
- **NPS пилотных команд ≥ 7/10** на вопрос «продолжите ли использовать после R&D». Открытый вопрос «что добавить» — для бэклога Phase 2.

Гипотеза опровергнута, если: < 50% операторов используют поток, или NPS < 5, или время ответа не меняется / растёт.

## 9. Открытые вопросы

Эти вопросы не блокируют старт разработки, но требуют решения до пилота:

1. **Хостинг для R&D-сервера.** Render / Railway / Yandex Cloud / VPS — окончательный выбор после оценки latency Битрикс → хостинг и стоимости managed RabbitMQ.
2. **Доступ пилотных клиентов к Маркету.** Регистрируем приложение в draft-mode для пилотов или используем коробочную установку через `client_id` + ручной URL?
3. **Бейзлайн для метрик.** Как именно снимаем «время ответа до внедрения» — самоотчёт команд или экспорт из их текущей системы?
4. **Юридические аспекты.** Оферта, политика обработки персональных данных (особенно — паролей IMAP/SMTP клиента). Отдельный документ, не часть этого ТЗ.

## 10. Оценка трудозатрат

При корректной инициализации стартера и без блокирующих сюрпризов:

| Блок | Трудозатраты (чел-недель, middle+) |
|---|---|

| OAuth-установка + регистрация коннектора | 0.5 |
| IMAP-poller + парсер писем | 1.0 |
